## Deferred from: code review of story-1.4 (2026-05-09)

- **`BIOS_TICK_ADDR` placeholder address overlaps the BIOS jump-table neighborhood.** `EQU 0xFA00` sits six bytes below `BIOS_CONIN EQU 0xFA06`; on a typical CP/M 2.2 BIOS (17 × 3-byte jumps = 51 bytes from base) the tick counter lands inside the jump-table region. Spec Task 1 mandates the architecture-listed placeholder values verbatim, so the value cannot be moved here. Story 1.12 (init/teardown, hardware bring-up) confirms real BIOS-jump-table addresses against MicroBeast docs/disassembly and must lay them out so the tick counter sits outside the jump-table. (Source: Blind Hunter + Edge Case Hunter.)
  - **Resolved by Story 1.12 (2026-05-13):** W1 confirmation against MicroBeast BIOS 1.6+ vendor header (`src/bios_1_7.inc`) found the architecture's earlier placeholders off by a full 4 KB AND with CONIN / CONIST slots swapped. Corrected in `inc/bios.inc`:
      - `BIOS_START` (new) = `0xEA00` (was-implicit `0xFA00`).
      - `BIOS_CONINST` = `BIOS_START + 0x06` = `0xEA06` (was `0xFA09`; symbol kept as `CONINST`, vendor name `CONIST`).
      - `BIOS_CONIN` = `BIOS_START + 0x09` = `0xEA09` (was `0xFA06`).
      - `BIOS_CONOUT` = `BIOS_START + 0x0C` = `0xEA0C` (was `0xFA0C`; IFNDEF guard preserved).

    The MicroBeast BIOS does NOT expose a free-running tick counter at any documented address — the architecture's assumption (line 1386) was wrong. Resolution: VIBE installs its own 60 Hz user ISR via `MBB_SET_USR_INT` (vendor entry at `0xFDC7`) that increments `input_tick_counter` (new 16-bit field in `inc/state.inc`). `src/init.asm`'s cold-start defensively uninstalls any pre-existing ISR before the LDIR fill, then installs `input_tick_isr` (10-byte routine in `src/input.asm`); `init_teardown` uninstalls before warm-boot per the vendor warning that user ISRs survive reboots but their TPA memory does not. `BIOS_TICK_ADDR` retired from `inc/bios.inc`; `tick_wait_one` reads `input_tick_counter` directly. 60 Hz vs the architecture's 50 Hz: `ESC_TIMEOUT_TICKS = 2` ≈ 33 ms, still inside NFR4's 20-40 ms target — no equate retune needed.
